# macOS 27.2 Control Center brightness research

This is a reverse-engineering note for WiredPad's `CGVirtualDisplay` screen. Native brightness now works: Control Center's slider, the brightness keys (Control-F1/F2 on a MacBook keyboard, or an external keyboard's keys with a window on the iPad screen), and iPad-side changes all stay in sync. See "Working native route" below. The earlier sections record the dead ends that led there.

## Observations

- WiredPad creates the screen with `CGVirtualDisplayDescriptor` in `Mac/VirtualDisplay.m`. Objective-C runtime inspection of the macOS 27.2 class shows display identity, pixel size, color primaries, queue, and termination properties, but no brightness capability or setter. It does expose `setDisplayInfoValue:forKey:`, whose accepted keys and effect on brightness have not been established.
- The macOS 27.2 dyld cache exports `ControlCenter.DisplayDevice.hasBrightnessControl`, `ControlCenter.DisplayController.refreshBrightnessState(for:)`, and `ControlCenter.DisplayController.setBrightness(_:on:)`. It also exports `DisplayServicesCanChangeBrightness`, `DisplayServicesGetBrightness`, and `DisplayServicesSetBrightness`. These symbols support a per-display brightness capability check, but symbols alone do not prove the exact call graph or eligibility rule.
- The native MacBook backlight has an `AppleARMBacklight` IORegistry service with `backlight-control = Yes` and `IODisplayParameters.brightness`. A `CGVirtualDisplay` is a WindowServer screen, not a physical backlight service. The presence of a display ID by itself does not create a brightness endpoint.
- Disassembling `DisplayServicesCanChangeBrightness` shows that it gets a `DisplayServicesClient` and asks for the `DisplayServicesCanChangeBrightness` property **for the supplied display ID**. Runtime inspection of `DisplayServicesClient` confirms `copyPropertyForKey:andDisplay:` and `setProperty:withKey:andDisplay:`. The client lives in `CoreBrightness.framework`, so changing the virtual display's vendor/product/name is not enough to publish that property.
- CoreBrightness contains `CBDisplayManager`, per-display `CBDisplayContainerMacOS`, `CBDisplayModuleMacOS`, `CBDisplayModuleSKL`, and legacy HID modules. `CBDisplayManager` has `copyDisplayInfo`, `copyDisplayList`, `containerForHandle:`, and `addContainer:`; `CBDisplayContainerMacOS` has `addHIDServiceClient:`; `CBDisplayModuleMacOS` reads and sets brightness. Its strings include `CBDisplayInfoDisplayID`, `CBDisplayInfoDeviceID`, `kUSBContainerID`, `DisplayUniqueID`, `CBDisplayVendorID`, and `CBDisplayProductID`. This strongly suggests that the display ID must be linked to a discovered brightness-capable device or service. The exact matching rules remain unverified.
- `BrightnessControl.framework` has separate `BCAppleBacklightBrtControl`, `BCHIDBrtControl`, `BCNativeBrtControl`, and VM-related control classes. Each real backend has `getNitsWithError:` and `setNits:error:`. The HID backend refers to `IOHIDDevice`, `DeviceUsagePage`, `DeviceUsage`, and `kUSBContainerID`; the native backend refers to DCP endpoints. These are distinct possible routes, so there is no single generic "Apple display HID" rule.
- Independent hardware research reports that Studio Display models expose a USB HID brightness feature report with a device-specific range, while one test on display firmware 17.0 found that macOS drove the physical backlight through a DisplayPort/Thunderbolt sideband even though HID report reads reflected the value. Those observations are model/firmware-specific and do not prove the exact macOS 27.2 route. In either case, native macOS control requires a discovered control service associated with the display, beyond EDID or a vendor ID.
- UIKit's public `UIScreen.brightness` property can adjust the iPad's main physical screen while WiredPad is in the foreground. Apple documents that the system restores the original setting after lock/unlock. This could implement iPad brightness control from WiredPad, but does not make the Mac's native Control Center slider recognize the virtual screen.
- WidgetKit offers third-party buttons and toggles in macOS Control Center. Its public Controls API does not expose a custom continuous brightness slider inside Apple's Display module.

## Live test on macOS 27.2 and iPadOS 26

- With WiredPad connected, the built-in MacBook display returned `DisplayServicesCanChangeBrightness = 1`; WiredPad's virtual display returned `0` (CG display IDs 175, 176, and 177 over successive sessions). `CGDisplayIsBuiltin` was `0` for WiredPad.
- The Mac app registered a separate CoreHID virtual Monitor Control device, WiredPad VID `0x5750` / PID `3`, with the virtual display ID and UUID in its properties. `hidutil list` showed it as `IOHIDUserDevice`, primary usage page `0x80`, usage `0x01`, transport `Virtual`. The existing touch DriverKit extension continued to match only PID `1`.
- A first descriptor with only a brightness Feature report worked for direct HID Get/Set, but did not change `DisplayServicesCanChangeBrightness`.
- A second descriptor matched the observed Studio Display HID layout more closely: report ID 1; brightness in 0.01-nit units, 400–60000; 16-bit fade duration; brightness Input and Feature fields. This also worked for direct HID Get/Set, but `DisplayServicesCanChangeBrightness` remained `0`.
- A direct Feature Set from 60000 to 48000 returned success. The next Feature Get returned 48080, showing that the value went through the iPad and came back after UIKit brightness quantization. The value was restored to 60000 after the test.
- Calling `DisplayServicesClient.setProperty:@YES withKey:@"DisplayServicesCanChangeBrightness" andDisplay:` reported success, but a read still returned `nil`; this is not a way to register a controllable display. Setting the same key through `CGVirtualDisplayDescriptor.setDisplayInfoValue:forKey:` likewise left the native capability at `0`, so that experiment was removed from the app.
- Reverse-engineering `BrightnessControl.framework` showed that `BCHIDBrtControl` matches `IOHIDDevice` with `DeviceUsagePage = 0x80` and `DeviceUsage = 0x01`. An `IOServiceGetMatchingServices` query with those exact conditions found WiredPad's virtual brightness HID without adding extra top-level IORegistry properties. `BCHIDBrtControl.copyAvailableControls` produced one control, whose `getNitsWithError:` returned 600 and whose container ID matched the virtual display UUID. Thus HID discovery and parsing are working.
- Registering the HID immediately after creating the `CGVirtualDisplay` was too early for the display UUID to resolve, leaving its brightness control without a container ID. Registering it after the display mode is selected resolves the UUID. This earlier point is retained in the code, although the native brightness capability is still `0`.
- `DisplayServicesClient.copyPropertyForKey:@"CBDisplayInfo"` returned a list containing only the MacBook's built-in display. WiredPad was present in `CGGetOnlineDisplayList`, but absent from CoreBrightness's display list. This is the most direct evidence that a display container, not a HID control, is missing.
- `CoreDisplay_DisplayCreateInfoDictionary(WiredPadDisplayID)` exposed `kCGDisplayIsVirtualDevice = 1` and the expected `kCGDisplayUUID`, but no `IODisplayLocation` or `kUSBContainerID`. The built-in display had `IODisplayLocation`. Putting `kUSBContainerID` in `CGVirtualDisplayDescriptor.displayInfo` did not cause it to appear in the WindowServer display-info dictionary or change the native capability; that temporary hardcoded-ID experiment was removed.
- A clean signed rebuild after removing that experiment still exposed two Quartz displays (MacBook ID 1, WiredPad ID 181), but `DisplayServicesCanChangeBrightness` remained `1` and `0` respectively. The global CoreBrightness `CBDisplayInfo` still contained only the MacBook display.
- Disassembly of the macOS 27 `DisplayServicesCanChangeBrightness` export shows that it queries a `DisplayServicesClient` property for the requested display ID. Directly setting that property for WiredPad did not create a durable capability.
- The current `BLControl` path in CoreBrightness obtains `<SLSBrightnessControl>` objects from a SkyLight client, then constructs `CBDisplayContainerSKL` and `CBBrightnessProxySKL` for each accepted control. Its `addDisplayContainerForBrightnessControl:` rejects an invalid display UUID before constructing the container. This explains why finding a `BCHIDBrtControl` by itself does not prove that the native path has enrolled the virtual screen. The virtual HID's UUID is valid, but no SkyLight brightness control for it has been observed.
- SkyLight has an `SLSBrightnessControlClient` and `SLVirtualDisplay` family. The latter exposes configuration type, subtype, options, display modes, and capabilities, but runtime method inspection found no explicit brightness delegate or setter on the virtual display. A standalone `SLSBrightnessControlClient` probe did not produce controls; it is not equivalent to the privileged daemon's SkyLight client, so this does not prove what the daemon sees.
- `SLSDisplayControlClient` exposes daemon/GUI connection methods and display notifications, while `SLSBrightnessControlClient` exposes brightness queries and requests. Runtime method inspection found no client method for registering a new brightness controller. A corrected standalone probe established an XPC service, reported `configured=1` and `enabled=1`, received a notification with raw value `0xD`, then returned an empty control list even for the built-in MacBook display. Therefore that client context cannot diagnose the daemon's actual per-display controls; the initial probe's crash was caused by treating the notification's non-object value as an Objective-C object.
- A fresh Objective-C runtime method-encoding probe confirms `SLSBrightnessControlClient` exposes only `initBrightnessControlClient:notifyQueue:notificationBlock:`, a variant with a notification type, `brightnessControls:`, and request methods for reads/updates; it has no registration method. The first initializer argument is an error-output pointer, not a registration token. `SLSDisplayControlClient` has `registerDaemonClient:` and `registerGUIClient:` for connecting as a client, not for publishing a new display brightness control. This narrows the client-side API surface but does not reveal the privileged WindowServer-to-`corebrightnessd` state payload.
- SkyLight's `SLVirtualDisplayConfiguration` exposes `type`, `subtype`, `options`, UTI, and identity fields; `SLVirtualDisplayCapabilities` exposes geometry/refresh properties. Neither inspected class exposes a brightness-capability field. The WindowServer executable is a thin launcher importing `SLXServer` from SkyLight, so the relevant server logic resides in SkyLight rather than that executable.
- The signed `/usr/libexec/corebrightnessd` has Apple-private `com.apple.private.SkyLight.brightnesscontrol` and `com.apple.private.SkyLight.displaycontrol` entitlements. WiredPad's signed host does not have these. This explains why a standalone SkyLight XPC client is not an authoritative replacement for the daemon's view. DriverKit's public family list does not include a display/framebuffer family; Apple's documented `IOFramebuffer` interface is deprecated and expressly not intended for third-party drivers. These facts do not by themselves prove that a native virtual brightness control is impossible, but they rule out treating the existing HID DriverKit extension as a display service.
- Objective-C protocol inspection identified `SLSBrightnessControl`: a per-display object with `displayId`, `uuid`, `containerId`, `brightnessAvailable`, `getNits:error:`, and `setLinearBrightness:error:`. SkyLight's `SLSDisplayController` implements this protocol. Its client builds controllers from WindowServer messages containing a display ID and capabilities; setting fields on a controller in WiredPad would affect only WiredPad's process, not the WindowServer's server-side display inventory.
- SkyLight's WindowServer implementation contains `WS::Displays::SLCADisplay::create_brightness_control_state()` and `WS::Displays::Manager::set_is_brightness_attached()`. By reading the loaded C++ vtable in a standalone process and resolving its function pointers with `dladdr`, the function's three gates were mapped exactly: it returns no brightness state when `is_airplay()` is true, when `is_sidecar()` is true, or when `is_helios()` is false. `WS::Displays::CAVirtualDisplay` inherits all three vtable entries unchanged. Its `make_display()` sets the virtual flag but does not set the Helios bit in the inspected initialization path. This explains why a correctly associated HID brightness control still does not create a native brightness controller for WiredPad's `CGVirtualDisplay`. `SLVirtualDisplay` and `CGVirtualDisplay` implement no Objective-C protocol that accepts an app-provided brightness controller.
- In `CAWSManager::virtualDisplayCreate`, the Helios bit (`SLCADisplay` flag at byte `0x9cc`, bit 4) is set when `SLVirtualDisplayConfiguration.type == 4`. The same creation path has a conditional `caller_has_entitlement` check for the Apple-private `com.apple.private.SkyLight.virtualdisplay` string. A directly initialized `SLVirtualDisplayConfiguration` of type 4 succeeded in a disposable standalone probe, so this entitlement check is not universal; it depends on the session/connection branch. The probe display was destroyed.
- A temporary signed WiredPad build used direct `SLVirtualDisplay` type 4 creation while keeping the existing virtual brightness HID registration for the new display ID. The screen appeared as Quartz display ID 186 and the HID appeared in `hidutil`, but `DisplayServicesCanChangeBrightness(186)` was still `0`, and CoreBrightness `CBDisplayInfo` still listed only the built-in MacBook display. The HID's UUID was not separately re-read in this run; its code derives the UUID from the new display ID. Merely setting the Helios bit and supplying that HID path is insufficient. A separate `CGVirtualDisplayDescriptor.setDisplayInfoValue:@4 forKey:@"SLVirtualDisplayType"` probe created a screen but also returned capability `0`; the CoreDisplay info did not show the type field, so the CG wrapper likely did not forward it. Both disposable screens and the signed Helios build were removed, and the normal signed WiredPad app was restored (new display ID 187, capability `0`).
- Further macOS 27.2 SkyLight disassembly narrows the missing link. `SLCADisplay::create_brightness_control_state()` first requires Helios (and excludes AirPlay and Sidecar), then builds a brightness state dictionary from the CA display's luminance fields. A `PresetShim` at object offset `0xbf8` supplies preset-specific nits when present, but there is a fallback branch when it is absent. Vtable resolution confirms that this fallback calls `is_external()` and `is_hdr_10()`. Thus absence of the preset shim alone is not evidence that a type-4 virtual screen cannot produce a brightness state. The state still did not lead to a CoreBrightness display container in the signed type-4 test.
- `WS::Displays::Manager::set_is_brightness_attached(displayID, bool)` sets a per-display flag at object offset `0x2f8`. Mapping the `Manager` vtable showed the method at slot `0x248`; tracing indirect calls found that `SLCADisplay::make_display()` sets it to `1` in a display-online callback and `0` in an offline callback, then broadcasts display-control notifications `5` and `6` respectively. Despite its name, this flag is driven by display lifecycle, so it cannot by itself explain why a type-4 virtual screen lacks a CoreBrightness container. The previous hypothesis that a separate HID-discovery path must set this flag was incorrect.
- CoreBrightness's `BLControl.handleSkyLightOnline` enumerates `<SLSBrightnessControl>` objects delivered by SkyLight and calls `addDisplayContainerForBrightnessControl:` for each one. That method creates `CBBrightnessProxySKL`, then `CBDisplayContainerSKL`. The latter has `addHIDServiceClient:`, but that is a method on an already-created container. Therefore the existing WiredPad HID cannot bootstrap the missing SkyLight display container by itself. This is an ordering constraint visible in the macOS 27.2 binary, not just an inference from the failed slider test.
- Unified logs from the signed Helios experiment and subsequent normal launch show `IOMobileFramebuffer` reporting `DisplayContainerID not found` while WiredPad virtual displays are online. The message lacks a display ID and also appears during normal launch, so it is a lead rather than proof that this specific missing property prevents brightness attachment. The same log window shows only display 1 in `com.apple.coreanimation:Brightness` commits. `corebrightnessd` logs mask most relevant keys as `<private>`, so they cannot establish which registration check failed.
- Vtable and disassembly inspection shows `SLCADisplay.copy_container_id()` reads its `CAWindowServerDisplay` at object offset `0x318` and asks CoreAnimation for that display's container ID. `CAVirtualDisplay.make_display()` does populate the backing CA display pointer; the missing result, if any, is downstream of that CoreAnimation lookup, not simply a null backing object. The separate WiredPad brightness HID currently advertises matching `kUSBContainerID`, `DisplayIdentifier`, and `CGDirectDisplayID` in IORegistry, so the ID is present on the HID side. A standalone process's `CAWindowServer.serverIfRunning` is null and cannot inspect the WindowServer's CA display object in place.
- A disposable `SLVirtualDisplayConfiguration` subclass injected `DisplayContainerID`, `DisplayIdentifier`, and `kUSBContainerID` into its serialized configuration dictionary for type 4. The server accepted the display and applied an 800×600 mode, but `CoreDisplay_DisplayCreateInfoDictionary` for the new display contained none of those injected keys, and `DisplayServicesCanChangeBrightness` remained `0`. The experiment was repeated and the virtual displays were destroyed. This rules out merely adding those three keys to the app-supplied configuration as a way to publish the missing display-side identity; it does not prove that the CoreAnimation backing display has no internal container ID.
- `CAWindowServerDisplay.brightnessAvailable` normally delegates to its backing `CA::WindowServer::Server` virtual method at vtable slot `0x170` (there is a special type-3 branch); `brightnessCapabilities` and `setBrightnessCapabilities:` use slots `0x178` and `0x180`. `CA::WindowServer::VirtualDisplay::new_server()` constructs a `CA::WindowServer::VirtualServer`. Runtime vtable resolution on macOS 27.2 proves that `VirtualServer` inherits the base implementations at all three slots: `brightness_capabilities()` returns null, `copy_brightness_capabilities()` returns null, and `update_brightness_capabilities(...)` immediately returns without storing anything. The `service_object()` slot also returns zero. By contrast, `IOMFBServer` overrides all four slots and delegates to its framebuffer display. Consequently, calling `setBrightnessCapabilities:` on a `CAWindowServerDisplay` backed by `VirtualServer` cannot publish brightness capability. This is a structural limit of the current virtual-display backend, beyond a missing HID usage or container UUID.
- SkyLight's XPC factory for the display-brightness-control service checks `com.apple.private.SkyLight.brightnesscontrol` on the connecting process; `corebrightnessd` has that private entitlement. A normal WiredPad host app cannot directly replace the missing server-side brightness registration through this service. This does not prove there is no other enrollment mechanism, but it closes the direct unprivileged XPC route.
- The installed Xcode 27.2 DriverKit SDK contains no display/framebuffer family headers. It has 13 family frameworks, including `VideoDriverKit`; its `IOUserVideoDevice`/`IOUserVideoStream` API is for video devices and streams, not a WindowServer display framebuffer. Apple's [DriverKit documentation](https://developer.apple.com/documentation/DriverKit) describes user-space device drivers, while its [`IOFramebuffer` reference](https://developer.apple.com/documentation/kernel/ioframebuffer) says the deprecated framebuffer class is not intended for third-party drivers. This is evidence against replacing `VirtualServer` with an `IOMFBServer` from an ordinary distributable DriverKit extension; it is not a proof that Apple has no private or future API for it.
- QuartzCore's four `CA::WindowServer::*Server` vtables in this binary are `Server`, `VirtualServer`, `IOMFBServer`, and `AccelServer`. The live vtable probe shows `AccelServer` inherits the brightness capability implementations from `IOMFBServer`, while `VirtualServer` inherits the empty base implementations. There is no separate brightness-capable virtual-server class in this framework build. An alternate SkyLight-only controller would have to bypass this CoreAnimation capability route.
- That SkyLight route is concrete: `XPCServiceClient::broadcastXPCNotification(SLDisplayStateDataType)` invokes `WS::Displays::Manager::display_state_data_for_type`. Its brightness-state branch iterates the manager's `hardware_displays` and `dfr_displays` sets, calls each display's `create_brightness_control_state()` virtual method, and serializes non-null states. `CAVirtualDisplay` inherits that method. This route does not consult the CoreAnimation `VirtualServer.brightness_capabilities()` slot while enumerating, so the empty CoreAnimation capability implementation alone does **not** prove that SkyLight cannot publish a virtual brightness controller. A normal `SLVirtualDisplay` creation path can add the created display to `hardware_displays` (manager offset `0x38`); a special session/type-4 branch instead adds it to the current display set. Which branch the signed WiredPad type-4 run used remains unverified. The decisive missing link is now whether SkyLight emits the virtual display's state to `corebrightnessd`, and if so why CoreBrightness does not retain a container.
- A disposable unsandboxed `SLVirtualDisplayConfiguration` type-4 probe created display ID 191 at 2160×1620 and destroyed it after inspection. `CoreDisplay_DisplayCreateInfoDictionary` contained a valid `kCGDisplayUUID` (`862FB11C-91D8-473C-AA4E-B24E3D946972`) and `kCGDisplayIsVirtualDevice = 1`; `DisplayServicesCanChangeBrightness` was still `0`. `CoreDisplay_CopyDisplayUUID` returned null, and `CoreDisplay_Display_CopyDisplayContainerID` returned the all-ones sentinel; the same two results were observed on the MacBook's built-in screen, so those API results are not specific evidence of a virtual-display identity failure. Running this probe inside the shell sandbox produced an `Invalid maximum size in pixels` initialization error; the same binary succeeded with normal WindowServer access, so that error was environmental.
- Disposable type-4 displays (IDs 192 and 193) stayed online for five seconds each while `DisplayServicesCanChangeBrightness` and `CBDisplayInfo` were polled once per second. Brightness capability remained `0` throughout; the `CBDisplayInfo` array count stayed at one (the built-in screen) in the ID-193 run. Both displays were destroyed. This rules out a simple short registration delay in the no-HID standalone probe, though the earlier signed WiredPad type-4 test with HID is the stronger end-to-end case.
- The SkyLight brightness-state enumeration has a manager-level gate: `display_state_data_for_type` checks a mode bit at manager offset `0x20` before collecting type-4 brightness states. `CAWSManager::initialize()` sets the low three bits of this word (`OR 0x7`), including the required bit, so this gate should be enabled in an initialized WindowServer manager; that is a binary inference, not a live read of the server object. When enabled, the function uses `hardware_displays` (offset `0x38`) plus `dfr_displays`, calls the virtual method at slot `0x708`, and serializes each non-null state. `virtualDisplayCreate` can add the new `CAVirtualDisplay` to the hardware-display set directly or to the current display set; `current_display_set` normally resolves to that same set. Thus the state path is not universally restricted to physical displays by its loop alone. Whether the type-4 state is emitted remains unverified. CoreBrightness's `addDisplayContainerForBrightnessControl:` constructs a container after checking the supplied display UUID against its invalid UUID sentinel; it does not require the `VirtualServer` capability slot itself at that point.
- Resolving every `SLCADisplay` virtual method called inside `create_brightness_control_state()` shows checks for AirPlay, Sidecar, and Helios, then identity, luminance, HDR, and white-point state. The dictionary this function builds has `DisplayUUID`, `DisplayID`, `DisplayType`, `Capabilities` (nits/headroom fields), `kUSBContainerID`, and related identity keys; no `BrightnessAvailable` key is constructed in this function. Whether the dictionary is actually emitted for the tested display is unverified.
- A disposable `SLSDisplayControlClient.registerGUIClient` probe successfully created an XPC client with the process's `SLSMainConnectionID` and reported `configured=1`, `enabled=1`. Its only notification was type 11 with `SLSDisplayControlNotificationErrorCode=1002` (`NSCocoaErrorDomain`), for each of three candidate client names (`com.apple.SkyLight.displaycontrol`, `BrightnessDaemon`, `com.apple.corebrightnessd`). It supplied no brightness-state payload. Successful client construction alone therefore does not establish access to the display-control state stream; this probe cannot replace the privileged daemon's view.
- SkyLight's `SLSBrightnessControlClient.handleServerMessage:` parses the `Capabilities` dictionary from a brightness-state entry, and sets `SLSDisplayController.brightnessAvailable` according to whether that dictionary is present. The state producer in `SLCADisplay.create_brightness_control_state()` conditionally adds `Capabilities`. The producer calls `brightnessCapabilities` on its backing `CAWindowServerDisplay` at offset `0x320`, then calls `mutableCopy`; when that is nil, it does not add the `Capabilities` key. This call chain is no longer just inferred: decoding the shared-cache Objective-C message stubs at `0x1880180b0` and `0x188010170` yielded the exact selectors `brightnessCapabilities` and `mutableCopy`. A separate stub at `0x18801baa0` resolves to `setBrightnessAvailable:` in the client parser. Because `VirtualServer` returns nil for `brightnessCapabilities`, the current CG/SL virtual-display backend lacks the native capability payload even when the type-4 Helios state is emitted. The end-to-end signed type-4 test confirms that CoreBrightness still does not expose the display. A live server-object read remains unavailable from the client process, but the binary path and runtime backend type are now pinned down.
- A disposable `SLVirtualDisplayConfiguration` type-3 screen (ID 194) was created at 2160×1620, observed for five seconds, and destroyed. Despite `CAWindowServerDisplay.brightnessAvailable` having a special type-3 branch, `DisplayServicesCanChangeBrightness` stayed `0` and CoreBrightness's display count stayed at one throughout. The `brightnessCapabilities` getter has no matching type-3 special case, and the SkyLight brightness-state producer requires Helios rather than Sidecar, so type 3 does not bypass the capability gap.
- An SDK-wide header search found framebuffer and display-service types only in the macOS Kernel/IOKit graphics headers; the DriverKit family headers contain none of `IOUserFramebuffer`, `IOFramebuffer`, `IODisplayConnect`, or a brightness-capability setter. The IOKit user-space graphics headers expose access to existing display services, not a way to publish a new framebuffer service. `DisplayServicesClient` provides property get/set and notifications, but no container-registration method; `CBDisplayManager.addContainer:` is used inside the CoreBrightness service. This leaves no identified app/DriverKit registration surface that can change the `VirtualServer` capability result. This is a search of the installed macOS/DriverKit 27.2 SDK and inspected runtime methods, not a claim about every private Apple mechanism.
- A fresh check of the installed app's code signature shows `com.apple.developer.hid.virtual.device` and `com.apple.developer.system-extension.install`, but no SkyLight brightness or display-control entitlement. `/usr/libexec/corebrightnessd` has both Apple-private `com.apple.private.SkyLight.brightnesscontrol` and `com.apple.private.SkyLight.displaycontrol`. A current runtime read still reports MacBook display ID 1 as `DisplayServicesCanChangeBrightness=1` and WiredPad virtual display ID 187 as `0`. The existing developer entitlements therefore authorize the HID transport, not publication of a native display brightness controller.
- A 2026-11-02 read-only recheck, with WiredPad running, found three active WiredPad virtual HID devices in `hidutil` (touch PID 1, volume PID 2, brightness PID 3). Quartz listed the built-in screen as ID 1 and WiredPad as ID 187. `DisplayServicesCanChangeBrightness` returned 1 for ID 1 and 0 for ID 187. `CoreDisplay_GetServiceIDForDisplayID`, `CGDisplayIOServicePort`, and `CoreDisplay_CopyDisplayUUID` returned zero or null for **both** screens in this user-process probe, so those calls do not distinguish WiredPad's missing registration from the built-in display. A standalone `CBDisplayManager` and `BLControl` instance also returned empty display lists, showing that constructing those private objects in a normal client process does not reproduce `corebrightnessd`'s inventory. This avoids treating the empty local lists as evidence of the daemon's actual internal state.

At this point the registration rule was still unknown, and the slider did not work. The later sections show that the missing pieces were Apple's legacy display IDs, a matching HID layout, and a hotplug of the virtual display.

## User-space-only display backend check

The display-driver alternative was checked against the installed Xcode 27.2 SDK and the live Objective-C runtime without installing or loading any driver. DriverKit has no published framebuffer/display family in this SDK. The kernel `IOFramebuffer` header does have `getApertureRange`, `getVRAMRange`, and `enableController`, and documents mapping framebuffer memory to user space; that is a kernel-extension route, not a method that the existing HID DriverKit extension can add. Apple currently describes `IOFramebuffer` as deprecated and not intended for third-party drivers. On Apple silicon, installing a custom kext requires Reduced Security and reboot, so this is not a suitable default for WiredPad.

An additional runtime probe of `CGVirtualDisplay`, `SLVirtualDisplay`, and their descriptor/configuration/capability classes found no selector exposing a composed frame, IOSurface, brightness capability, or brightness callback to the creating app. `CAWindowServerDisplay` does expose `displayedSurface`, `currentSurface...`, `brightnessCapabilities`, and `setBrightnessCapabilities:`, but it is a server-side object. The existing app-created virtual display uses `VirtualServer`, whose capability setter is a no-op; the standalone process does not have a running `CAWindowServer` object through which to modify the WindowServer display. These observations narrow the non-kext path: an ordinary `CGVirtualDisplay`/`SLVirtualDisplay` property, a second HID collection, and a matching UUID cannot by themselves register native brightness capability or expose the final composed pixels. They do not rule out an as-yet-unidentified Apple-provided user-space display service.

For capture, the current `SCStream` uses ScreenCaptureKit, whose documentation requires screen-recording permission. Substituting another capture API is not evidence that the permission or sharing indicator disappears. A framebuffer-backed display might allow a different read path, but this has not been demonstrated on macOS 27.2 and would still need separate privacy and brightness tests before adoption.

## Apple display control path, separate from video

The previous explanation that a Studio Display-style brightness control requires the *same driver* to render pixels was too strong. Video transport and brightness control are separable. On this Mac, `AppleUSBDisplays.kext` has `IOKitPersonalities` matching Apple USB display interfaces and a `Gestalt.hasBrightness` setting with HID monitor-control usage `0x00820010`; its provider is `IOUSBHostInterface`, not a framebuffer. This specific kext matches older `0x92xx` Apple display products and should not be asserted to be the Studio Display's active driver. `com.apple.AppleUserHIDDrivers.dext` has a Studio Display (USB product 4372) property merger that only sets `HIDResetDisabled`; the `AppleUSBHostMergeProperties` personality for the same product selects USB configuration 3. Neither personality publishes a framebuffer.

`ProDisplayLibrary.framework` contains `AppleDisplayHIDDevice` and `HIDDataStore` Swift types. Its exported symbol `AppleDisplayHIDDevice.init(container: String)` directly uses a container string; `DisplayID.ContainerIDDataBlock` parses a UUID. `HIDDisplay.framework` exposes `HIDDisplayInterface` with `initWithService:`, `initWithContainerID:`, `containerID`, and HID-device matching methods. This is further evidence of an independent display-control side channel, but the installed binary names alone do not establish the exact Studio Display brightness call sequence. In a read-only probe, `HIDDisplayInterface.initWithService:` accepted WiredPad's brightness HID and returned its correct container UUID. The base class's `getHIDDevices` implementation unconditionally returns nil, so `initWithContainerID:` returning nil on that base class is expected and does **not** show a failed automatic match. Its preset, user-adjustment, and device-management subclasses also returned nil for WiredPad's container ID; these interfaces may require different HID collections than monitor brightness. The direct `BCHIDBrtControl` probe remains the relevant evidence that WiredPad's brightness report itself is parsed correctly.

The exported `AppleDisplayHIDDevice` methods primarily manipulate presets, user-adjustment ranges, and reference-mode data, rather than exposing a simple `setBrightness` entry point. Its container-based constructor confirms that Apple can pair a display-control HID channel with an independently created screen, but it does not show that this library registers a new screen with Control Center. The actual macOS brightness candidate remains the `BrightnessControl`/`CoreBrightness` chain, where WiredPad's HID report works but the virtual screen has no published brightness capability. A true Studio Display trace would need attached hardware; the on-disk Studio-specific USB personalities alone do not reveal every runtime association rule.

The older `AppleUSBDisplays` personality's `HIDDisplay=1` flag was tested as a specific automatic-discovery candidate. `IORegistryEntrySetCFProperty` could not update the running virtual HID (sandboxed call returned `kIOReturnNotPermitted`, ordinary unsandboxed call returned `kIOReturnUnsupported`), so two signed WiredPad test builds supplied the property at `HIDVirtualDevice` creation: one with `HIDDisplay=1` plus `HIDDefaultBehavior="Display"`, then one with `HIDDisplay=1` alone. Both created the Quartz virtual screen but failed to publish **any** WiredPad virtual HID devices. `DisplayServicesCanChangeBrightness` remained 0. After restoring the original signed app and source, the touch and brightness HID devices reappeared immediately and the display remained at capability 0. This AB check shows that injecting this AppleUSBDisplays property into `CoreHID.HIDVirtualDevice.Properties.extraProperties` is not a viable fix; it does not by itself identify which internal validation rejects the virtual HID. No experimental flag remains in the app.

The currently running WiredPad brightness HID (`IOHIDUserDevice`, PID 3) has no `corebrightnessd` `IOHIDLibUserClient` child. The one `corebrightnessd` HID client observed nearby belongs to the MacBook's **keyboard backlight**, not WiredPad. This corrects an easy misreading of the flattened `ioreg` output. It is consistent with CoreBrightness not enrolling WiredPad's HID as a controllable *display*, despite a direct `BCHIDBrtControl` probe being able to enumerate and set it. The next useful comparison is a live Studio Display IORegistry and CoreBrightness state on hardware that has one attached, or a precise trace of the installed Apple control framework's discovery filter. Do not infer from the missing client alone that `VirtualServer` is the only cause; the control and video paths must be checked separately.

An exhaustive runtime scan for CoreBrightness display-registration selectors found `CBDisplayManager.addContainer:`, `BLControl.addDisplayContainerForBrightnessControl:`, `VMBLControl.addDisplayContainerForBrightnessControl:`, and notification-observer registration methods, but no ordinary client-facing `registerDisplay`/`publishDisplay` selector. `VMBLControl` is a separate virtual-machine host protocol: its disassembly includes `connectToHost`, host brightness transactions, and `VMDisplayModule`, so its container builder is not evidence that an app-created `CGVirtualDisplay` can enroll itself. `BLControl` remains the local daemon path driven by SkyLight's display controls. The scan does not rule out a non-Objective-C or undocumented XPC route.

`TMBLControl` was checked as another possible registration branch. Its method list includes `openSKLClient`, `handleSkyLightOnline`, `addDisplayModuleForBrightnessControl:`, and `clearDisplaySet`; the `openSKLClient` disassembly initializes a SkyLight client and notification block. It therefore also consumes a SkyLight-supplied brightness-control inventory rather than exposing an independent app-side display registration endpoint. Its exact product role was not established. This narrows the remaining non-kext option to finding a way for the normal WindowServer/SkyLight inventory to report a valid brightness control for the app-created virtual screen, or a separate privileged service route that has not been identified.

## How a real external display gets its capability (IOMobileFramebuffer pairing)

A 2026-11-02 probe filled in the step between the HID control and `CAWindowServerDisplay.brightnessCapabilities` for real (DCP-driven) displays:

- `IOMobileFramebuffer.framework` exports `IOMobileFramebufferGetBrightnessControlCapabilities` and `IOMobileFramebufferGetBrightnessControlInfo`. Its lazy loader `iomfb_bc_load_lib` `dlopen`s `BrightnessControl.framework` and resolves `BCBrtControlNewMonitorForAllDisplaysWithHandler`, `BCBrtControlGetContainerID`, `BCBrtControlGetMinNits`, `BCBrtControlGetMaxNits`, `BCBrtControlGetCapabilities`, `BCBrtControlGetIsValid`, `BCBrtControlSetDisplayInvalidHandler`, `BCBrtControlSetNits`, and `BCBrtControlSetDisplayService`. So the framebuffer client inside WindowServer monitors **all** BrightnessControl controls (including `BCHIDBrtControl`) and pairs one with its framebuffer.
- `GetBrightnessControlCapabilities` returns the object at framebuffer-client offset `0x10e8` only when the byte at `0x10b1` (a "paired" flag) is 1; otherwise it returns nil. `GetBrightnessControlInfo` returns `kIOReturnNotReady`-class `0xe00002c0` unless the same flag is set. In an ordinary process, all three `IOMobileFramebufferShim`s (built-in and two unused external ports) returned nil / `0xe00002c0`: the monitor runs in WindowServer's own client, so this probe cannot see the paired state, only the structure.
- The pairing key on the display side is the framebuffer's `DisplayContainerID` kernel property. WindowServer's unified log repeatedly shows `(IOMobileFramebuffer) kern_CopyProperty key : DisplayContainerID not found` for unused/internal shims. For an external display this ID comes from DCP; `ProDisplayLibrary`'s `DisplayID.ContainerIDDataBlock` matches the DisplayID 2.0 Container ID data block (a 16-byte UUID that also appears as the USB devices' `kUSBContainerID`). The built-in panel instead pairs through `BacklightMatching = {IOPropertyMatch = {backlight-control = Yes}}` with `AppleARMBacklight`.
- Inferred Studio Display chain (binary structure, not traced on attached hardware): DisplayID Container ID → DCP framebuffer `DisplayContainerID` → IOMFB matches a `BCBrtControl` (USB HID monitor-brightness, or DCP-native) with the same container ID → min/max nits and capabilities → `IOMFBServer.brightness_capabilities()` → SkyLight Helios `create_brightness_control_state()` emits `Capabilities` → `corebrightnessd` builds `CBDisplayContainerSKL` and attaches the HID → `DisplayServicesCanChangeBrightness = 1` → Control Center slider.
- WiredPad's live brightness HID already advertises `kUSBContainerID = DisplayIdentifier = 7C669EA0-F626-4EC1-A4E7-4B3B4B643389` (CG display 198), so the control half of the pair exists. The missing half is a framebuffer client that runs this BrightnessControl monitor. `CGVirtualDisplay`/`SLVirtualDisplay` use `CA::WindowServer::VirtualServer`, which has no IOMFB object, so no `DisplayContainerID` lookup or BC pairing ever happens for it. That makes the earlier `VirtualServer` capability finding concrete: the gap is the IOMFB pairing step, not the HID descriptor or the UUID.

## Legacy HID path (Apple Thunderbolt/LED Cinema-class displays)

- Control Center does not call `DisplayServicesCanChangeBrightness` itself. It imports `DisplayServicesGetBrightness`, `DisplayServicesSetBrightnessSmooth`, and `DisplayServicesClient`. A live probe shows every one of these resolves through `corebrightnessd`: for the built-in display, `DisplayServicesGetBrightness` returns 0 and the `DisplayServicesBrightness` property is set; for WiredPad (ID 198), Get returns error 1000 and every property is nil. `corebrightnessd`'s container list is the only authority.
- `CBDisplayContainerSKL initWithBrightnessControl:andSystemContext:` sets `legacyHID = +[CBDisplayModuleHIDLegacy supportsBrightnessControlForDisplayWithVID:control.vendorID andPID:control.productID]`. That check is true only for display vendor `0x0610` and product `0x9226`, `0x9227`, or `0x9236`. When true, `CBDisplayModuleHIDLegacy` matches `IOProviderClass = IOHIDDevice`, `VendorID = 1452` (USB `0x05AC`), `ProductID = <display product>`, `DeviceUsagePage = 0x80`, `DeviceUsage = 1`, plus `SerialNumber = %08lX` of the display serial for `0x9227`. Its arrival handler reads brightness, ALC state/reset, and a vendor-page `0xFF92` "Mac mode" element. This is the one container flavor that gets brightness purely from a USB HID rather than from framebuffer capabilities.
- That module is still created only inside a `CBDisplayContainerSKL`, which `BLControl` creates only for a SkyLight-delivered `SLSBrightnessControl`. A disposable `SLVirtualDisplayConfiguration` type-4 (Helios) screen with vendor `0x610`, product `0x9226` (CG reported exactly those values; display 199) kept `DisplayServicesCanChangeBrightness = 0`. A live `log stream --level debug` of `corebrightnessd` during that screen's lifetime contained no `incoming notification type`, `SkyLight is ONLINE`, or `adding container` messages: SkyLight sent `corebrightnessd` nothing for that virtual screen. WindowServer logged `Add 199 to the console display set`, the same path as WiredPad's normal `CGVirtualDisplay`. Thus the legacy HID route is blocked upstream in SkyLight, before the vendor/product check is even reached.
- `OSD.framework`'s `OSDManager.showImage:onDisplayID:priority:msecUntilFade:filledChiclets:totalChiclets:locked:` exists on macOS 27.2 and takes a target display ID. That is the API MonitorControl-style tools use to show the system brightness bezel on a display macOS itself cannot control. A test call targeting WiredPad's display 198 returned without error. The shell lacked screen-recording permission, so whether the bezel was drawn was not captured.

## Working native route (2026-11-02): legacy Apple display HID

Native brightness now works for WiredPad's `CGVirtualDisplay`, after a `corebrightnessd` restart:

- `corebrightnessd` does build a `CBDisplayContainerSKL` for an ordinary `CGVirtualDisplay` (log: `DisplayType=2 … Capabilities=(null) … legacyHID=0`), but only while enumerating SkyLight controls at its own start (`SkyLight is ONLINE`). Adding a virtual display later produced no notification or container. A type-4 `SLVirtualDisplay` got no container even at restart. `CBDisplayInfo` lists only brightness-capable displays, so its count was never evidence of a missing container.
- With the display's vendor/product set to `0x0610`/`0x9226`, the container logs `legacyHID=1` and matches `IOHIDDevice` with `VendorID=1452`, `ProductID=37414`, `DeviceUsagePage=128`, `DeviceUsage=1`. A CoreHID virtual device may use Apple's USB VID `0x05AC`.
- For product `0x9226` the arrival handler is called with `matchEDIDserialNumber:YES`: it gets Feature report 2 (21 bytes), treats bytes 1–20 as the EDID header, and requires the little-endian serial at EDID offset 12 to equal the display's serial. It then opens the device, sets Mac mode, reads state, and uses Feature elements Brightness (`0x82:0x10`, value = level × logical max), ALC state (`0x82:0x66`), ALC reset (`0xFF92:0xEB`), and Mac mode (`0xFF92:0xE1`).
- With that layout (`Mac/CoreBrightnessDevice.swift`), the log shows `CBDisplayModuleHIDLegacy.205: brightness service arrived`, `DisplayServicesCanChangeBrightness(205) = 1`, `DisplayServicesGetBrightness = 1.0`, and `DisplayServicesSetBrightness(205, 0.4)` wrote raw 409/1023 into the HID brightness report.
- Remaining gap: the container exists only if the display is online when `corebrightnessd` starts. A display created afterwards needs a way to make `BLControl` re-enumerate SkyLight controls.
- The user confirmed the Control Center slider changes the iPad's brightness after the restart.

### Why a newly created virtual display is not picked up

- `BLControl handleSKLClientNotificationWithType:andPayload:` handles type 3 (display connect: `addDisplayContainerForBrightnessControl:`), 4 (disconnect: remove), 8 and 14 (logical/power state), 12 (`SkyLight is ONLINE`: `handleSkyLightOnline` re-enumerates every control), and 13 (offline). `handleSkyLightOnline` is called only from that handler; `openSKLClient` only from `-[BLControl start]`.
- In SkyLight, `XPCServiceClient::broadcastXPCNotification(SLDisplayStateDataType)` (the full brightness-state stream) is called only from `CAWSManager::initialize()`. The per-display type 3 is sent from `CAWSManager::process_deferred_hotplug_events()` (hardware hotplug) and from `SLCADisplay::process_display_connect`. A virtual display's first apply does reach `process_display_connect` through `set_display_digital_modes(…, bring online)` (log: `Will bring display … online`). But there the type 3 broadcast is inside the clamshell branch (`has_clamshell()` / `is_lid_closed()`), so it is skipped for a virtual display.
- So nothing a normal process does after `corebrightnessd` starts makes it enumerate a new virtual display. WiredPad keeps its `CGVirtualDisplay` across iPad reconnects (`heldDisplay`) and recreates the brightness HID each session, which the legacy module picks up through its standing `IOServiceFirstMatch` notification. A re-enumeration is therefore needed once each time the display is created (normally once per app launch). The launchd label is `system/com.apple.corebrightnessd`; restarting it requires root.

### Enrolling a new virtual display without restarting corebrightnessd

- SkyLight's `config_command_softplug` (a display-configuration command) goes through `CAWSManager::inject_client_api_softplug` and `inject_hotplug` into the ordinary hotplug path, which sends `corebrightnessd` type 3/4 for that display. The client side of this command is `CGSConfigureDisplayEnabled` (CoreGraphics re-export of `SLSConfigureDisplayEnabled`) inside a `CGBeginDisplayConfiguration` … `CGCompleteDisplayConfiguration(kCGConfigureForSession)` transaction.
- Disabling and then re-enabling a `CGVirtualDisplay` logs `[Display:Hotplug] Processing hotplug "out"/"in" … (API)`. `corebrightnessd` then logs `initialised container … legacyHID=1` and `brightness service arrived` for the same display ID, while staying the same process. The display ID is kept. Right after `applySettings:` the replug had no effect; WiredPad replugs once the display is online (after mode selection and HID activation, before capture starts), and only if `DisplayServicesCanChangeBrightness` is still 0.
- Destroying a virtual display is not an unplug to `corebrightnessd`: its container stays and grabs the next brightness HID with the same VID/PID. Disabling the display before releasing it logs `removing container`. WiredPad does this in `WiredPadDestroyDisplay`, which also runs on app termination.

### Display name and Apple's override files

- CoreDisplay merges `/System/Library/Displays/Contents/Resources/Overrides/DisplayVendorID-610/DisplayProductID-<id>` into the display info, so the virtual display's own name loses. For `0x9226` and `0x9236` (LED Cinema Display) the file also replaces the primaries and adds a gamma table, which macOS used for the WiredPad screen's profile. The `0x9227` file (Thunderbolt Display) sets only the name, so WiredPad uses `0x9227`: the screen keeps its own primaries and an identity transfer.
- For `0x9227` the legacy module matches the HID's `SerialNumber` against the display serial as `%08lX` and skips the EDID-header check. So the HID carries serial `00000002` and has no report 2.
- Showing "WiredPad" would need an override file installed with admin rights under `/Library/Displays/…`, which would also rename a real Thunderbolt Display. Not done; the screen shows as "Thunderbolt Display".

## Packaging with the existing touch driver

The host app already creates a `CoreHID.HIDVirtualDevice` for ten-point touch (`Mac/CoreTouchDevice.swift`). It uses report ID 1 and has get/set feature-report delegate methods. The bundled DriverKit extension matches **only** WiredPad VID `0x5750`, PID `1`, primary usage page `0x0D`, usage `0x04`, then converts touch input reports to digitizer events. Its display link is `CGDirectDisplayID` plus a display UUID copied from the virtual screen.

It is possible at the HID descriptor level to add another top-level collection and feature-report ID to that virtual device, with get/set handled by the same host delegate. The touch DriverKit parser would continue to consume only report ID 1. However, CoreBrightness may match a brightness service by **primary** usage, USB container identity, transport, or other properties. A second collection in the touch HID device might therefore never become an eligible `BCHIDBrtControl` service.

The Mac app now creates a second virtual HID device for monitor brightness and forwards its Feature Set requests to iPadOS, which applies `UIScreen.brightness`. The device and transport work, but a shared app bundle plus display ID/UUID do not cause CoreBrightness to associate the HID service with the virtual display. The missing SkyLight/WindowServer brightness controller or display-service registration path remains unidentified; the existing HID DriverKit entitlement does not supply it.
